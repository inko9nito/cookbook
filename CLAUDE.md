# Cookbook — instructions for Claude

Personal recipe PWA for one user on an iPhone. Mobile-first, iOS-native feel. Full plan: `docs/PLAN.md`.

## Non-negotiable: never hand-roll iOS UI
- UI library is **Framework7 v9 + framework7-react**, theme locked to `ios`.
- Use Framework7 components for every sheet, popup, drawer, page transition, swipe gesture, action sheet, picker, stepper, sortable list, swipeout, toast, searchbar, and tab bar.
- Use the **Framework7 router** (not React Router) so iOS push transitions and swipe-back work.
- Swipe-back is **iOS's own back gesture** (Safari and the home-screen app both have one): the views use Framework7's `browserHistory`, so each page is a history entry and the gesture goes back a page inside the app. Framework7's `iosSwipeBack` is off, or one swipe goes back twice and leaves the app (it went to Google's sign-in page). Keep it that way in `src/App.tsx`.
- Do **not** write custom CSS or JS for animations, transforms, gestures, or z-index. Do not wrap `Page` content in custom scroll containers.
- Custom styling is limited to colors, spacing, corners and typography, preferably through Framework7 CSS variables.
- **No iOS 26 look.** The user rejected Framework7 v9's liquid glass, floating tab bar and capsule nav buttons. The "Not iOS 26" block in `src/theme/cookbook.css` restyles them to the agreed design (flat docked tab bar, left titles, separate round buttons). Keep new screens consistent with it. It also turns off Framework7's **backdrop blur** on the header, its buttons, the search field and the tab bar: iPhone Safari sometimes left those blurred layers blank in the page colour, so headers and search bars vanished (#25). Keep it off; `check:ui` (01a) fails if a bar is blurred again. For the same kind of Safari bug (#123: now and then a header stopped being drawn, the whole of it or its background, until the app was restarted): Safari skips a still layer that has Framework7's `backface-visibility: hidden`, so headers (and the docked bars' lines) have `backface-visibility: visible`; each header also has a drawing layer of its own from the start (`will-change: transform` on `.navbar`, a hint only: no transform, Framework7's hide-on-scroll still slides it), so it's always drawn the same way; and Framework7's empty masked strip for the blur (`.navbar-bg::before`) is off. `check:ui` 01a2. Never give a still element `backface-visibility: hidden`.
- If Framework7 lacks something, **stop and ask the user** before building a custom version.
- **Approved exception (Nov 2026):** cook mode's split screen (Ingredients over Directions, each half scrolling on its own) with a hand-built drag handle between them (`src/components/CookMode.tsx`), because Framework7 has no split view. The handle only sets the top half's height (pointer events, no transforms, animation or z-index: it is last in the markup and each half has `isolation: isolate`, so it paints on top). Don't reuse it elsewhere without asking.
- **Approved exception (Nov 2026, issue #116, the user asked for both):** cook mode's recipe tabs **drag to reorder** (`src/components/CookTabs.tsx`), because Framework7's Sortable only does vertical lists. Hold a tab 350ms (a finger that moves first is scrolling the strip) and it lifts (`.ck-cook-recipe-lifted`, `z-index: 1` so it passes over the tabs after it); it follows the finger with a `translateX`, a non-passive `touchmove` stops the strip scrolling meanwhile, the others slide to their new places (Web Animations, 180ms) and it settles where it's let go; order is `session.open` (`moveRecipe`). And **✓ / ✕ transitions** (`CookMode.tsx`, `goes()`): ✕ drops the recipe away and folds its tab up; ✓ ticks every box, turns its tab's photo into a ✓, then lifts the recipe away and folds the tab; the next recipe fades in. Web Animations, none with Reduce Motion. Don't reuse either elsewhere without asking.
- **Approved exception (Nov 2026):** photo cropping uses **Cropper.js 1.x** (`src/components/PhotoCropper.tsx`), because Framework7 has no cropper. It runs inside a Framework7 Popup, with a fixed **square** (#51: every recipe photo shows square, so the crop is what shows) and the rest of the photo dimmed around it (Cropper's modal, viewMode 1: the photo always covers the square; pinch to zoom, drag to move). Don't reuse the turn elsewhere without asking. Swiping through photos and full-screen zoom stay Framework7 (Swiper, Photo Browser).
- **Approved exception (Nov 2026):** Settings → Version has a refresh icon that **spins** (a CSS rotation, `.ck-spinning`) while it checks for a new version of the app and reloads, because the user asked for exactly that instead of Framework7's preloader dialog and a toast. Don't reuse the spin elsewhere without asking.
- **Approved exception (Nov 2026, issue #90):** a cookbook's header (`CookbookPage`) has one scroll listener of its own, because Framework7 has no header that scrolls away like the user's mockup. The header (colour, plates, name, counts, its own search bar) is page content. The listener sets `--ck-hero-p` (0 → 1 while the plates scroll under the bar: the plates and colour fade out, as the user asked), `.ck-hero-solid` (the bar's background, only once the fade is done: the user wants the bar fully see-through until then), `.ck-hero-titled` (the title, once the name has gone all the way under the bar, as iOS does it: never in the bar and on the page at once; the count under the name hides then) and `.ck-hero-docked` (Framework7's docked search bar, once the header's reaches the bar; the header's is then hidden, so only one ever shows), and once docked hides/shows the title row with Framework7's own `navbar.hide()`/`show()` (`hideNavbarOnScroll` would hide it after 44px, with the header still on screen). Framework7's large-title navbar was tried and rejected by the user (odd slide, a solid colour band). Don't reuse it elsewhere without asking.
- **Approved exception (Nov 2026):** the **launch loader** (`index.html`, the user asked for it): while the app starts, the app icon's cooking pot sits in the middle of the page and its lid rocks like a cartoon pot about to boil over, one side up and then the other (the user's direction: cartoon-like and fluid, no steam). CSS keyframes on transforms only, on whole elements: the pot (a cartoon squash and stretch as the lid lands) and the lid in two nested layers, one per hinge; still with reduced motion. It's plain HTML and CSS, so it shows before the app's code loads; `LaunchLoaderDone` (`src/data/launch.ts`) takes it away in one frame, no fade (a fade showed a ghost pot over a washed-out page, which the user saw as a flash, and iOS kept that half-faded frame as the app's picture for the next launch), as soon as the app can draw its first screen (the user's direction: the pot covers only the app starting up; recipes and photos load under the screens' skeletons, #35). It never waits for recipes or photos (waiting for photos by loading and decoding copies with `img.decode()` left them blank in the grid on iPhone Safari). In the home-screen app it also waits for the page to reach the screen's full height (drawn before that, the app was laid out short: its tab bar floated above the bottom with white below), 2.5s after the page starts at most; never waiting longer for the animation's sake. `#app` has `isolation: isolate` so the loader, after it in the page, covers it without a z-index. Automated checks leave it out (`navigator.webdriver`) unless the address has `?loader`, which also keeps it on screen; `?loader=slow` plays it at a quarter speed (`check:ui` 37a–b). Screens still use skeletons, never this loader. **Launch images** (`public/launch/`, the `apple-touch-startup-image` links in `index.html`): pictures of the loader, still with the lid at rest, one per iPhone screen size, which iOS shows the moment the home-screen app is tapped, so there's no blank screen before the page paints (the same as the user's HPDE app). `npm run launch-screens` (`scripts/make-launch-screens.cjs`) writes both from `index.html`'s own loader: **run it again after changing the loader**, and add a row there for a new iPhone size. They're left out of the offline cache (`globIgnores` in `vite.config.ts`). In the home-screen app the page starts out about 50 points shorter than the screen and grows a moment later, so there the loader is laid out on `screen.height` (`--ck-launch-h`, set by a script in the head), keeping the pot exactly where the launch image has it; centred on the page, it drew 25 points higher and then dropped (`check:ui` 37c; 37d: the loader waits for the full height). Don't reuse it elsewhere without asking.
- Scroll state for bars (#99): Framework7 has no class for "this page is scrolled", so `useAtTop()` (`src/components/ui/atTop.ts`, one passive scroll listener, set through the Page's `onPageInit`) puts `ck-at-top` on Recipes and cookbook pages; their docked search bar shows its line and shadow only once scrolled. It only toggles a class (no animation). The Planner's week strip keeps both always.
- The recipe page's bar (#87) is Framework7's **transparent navbar** (`transparent`): see-through over the photo, fading to solid as the page scrolls. With `hideNavbarOnScroll`, Framework7 stops the fade while the bar is slid away, so `cookbook.css` keeps the strip under the clock solid then.
- Check the Framework7 v9 docs for a component's props before using it. Don't guess.

## Seeing an issue's screenshots and videos (never say they're blocked)
The user attaches screenshots and screen recordings to issues and expects them looked at. `github.com/user-attachments/...` links can't be fetched from a cloud session (the GitHub proxy refuses non-repo paths, and `/markdown` too), but the issue's **rendered HTML** from the repo API carries signed `private-user-images.githubusercontent.com` addresses (valid 5 minutes), which download fine:
1. `curl -sS -H "Accept: application/vnd.github.full+json" https://api.github.com/repos/inko9nito/cookbook/issues/<n> -o issue.json` (comments: `.../issues/<n>/comments` with the same header; each has `body_html`). Save to the scratchpad.
2. Pull the `<img src="…">` / `<video src="…">` addresses out of `body_html` (unescape `&amp;`), write each to a file, then `curl -sS -o shot.png "$(cat url.txt)"` and look at it with Read.
3. A video only becomes a `<video>` (with a signed address) when its link is **on a line of its own**; inline in a sentence it stays a plain `github.com/user-attachments` link. Then edit the issue description (the plan lives there anyway) to put the link on its own line, and fetch again.
4. Videos: `ffmpeg -i vid.mov -vf "fps=3,scale=300:-1" frames/f%02d.png`, then `ffmpeg -i "frames/f%02d.png" -vf "tile=6x3" -frames:v 1 sheet.png`, and Read the contact sheet.

## Workflow: preview before merging
- Every change goes to the user as a **pull request with a Netlify deploy preview**: push to the working branch, open a PR into `main` if none is open (or keep updating the open one), and give the user the preview link `https://deploy-preview-<PR number>--cookbk.netlify.app` each time it updates.
- **Merge only when the user asks.** They look at the preview on the phone first.
- **Never watch (subscribe to) PRs in this repo**, and don't ask whether to. The user says when to merge.
- **Plans live in their GitHub issue.** For an issue worked through in steps (e.g. #14, the Prepear import), keep the plan in the issue's description: tick steps as they land, note decisions and open questions, and add a dated line under Status at each milestone (PR opened, waiting on the user, merged). Update it as part of the work, without being asked. No private data in it (the repo and its issues are public).
- Preview links are public, and a preview has its own copy of the production database (real recipes). Previews share the photo store with production.

## Design: the Cookbook design system
- Spec: `DESIGN.md`. Tokens and Framework7 mapping: `src/theme/cookbook.css`. Visual check: in-app Settings → Style Guide.
- The user picked each component's shape from a different design system (RED, Starbucks, Headspace, Pinterest, Instacart, DoorDash; recipe cards from Prepear itself) and unified all colors: Cool grey neutrals, **Tomato `#e4572e`** accent, **Parkinsans** at 90% for all text (issue #135; Fredoka + Nunito before). Light mode only for now.
- Never hard-code colors in components. Use `var(--ck-*)` tokens or Framework7 variables. Add new tokens to `cookbook.css` and `DESIGN.md` (both the YAML front matter and the prose) together.
- **Edges (#55):** a shaped button at a popup's edge is as far from the top as from the sides, 16px (`--ck-edge-inset`; popup headers are 72px: 16 + 40px buttons + 16). A sheet keeps 24px from every edge (`--ck-sheet-inset`, mapped onto Framework7's block, list, toolbar and calendar variables in `.sheet-modal`): its header text 24px from the top and sides, its content lined up with it. `check:ui` flags any open popup or sheet that breaks either.
- **Empty states (#118):** a screen with nothing on it uses `EmptyState` (`src/components/ui/EmptyState.tsx`) and the rules in `DESIGN.md` → Empty states: hide what works on things that aren't there (search, view switches, sort, counts), a few words, one button that opens the same choices as the screen's +, no instructions. An empty *part* of a screen keeps the small inline look (#82). One icon on a white circle (the user rejected plates there: they mean cookbooks); Style Guide → Empty state shows it.
- Tomato for **text** is `--ck-accent-ink` `#c4421c` (also Framework7's theme color); bright Tomato `--ck-accent` is for fills only. Muted text is `#6e6e73`. These were chosen to pass WCAG AA contrast.
- **Icons: Lucide only** (`lucide-react`, the same library as the user's other apps). Use the shared props in `src/components/ui/icons.ts` (`navIcon`, `tabIcon`, `inlineIcon`). Don't add another icon set. Framework7's built-in glyphs (back chevron, list chevrons, checkmarks, search magnifier) stay as they are.
- The repo is public. The user explicitly approved committing the sample photos in `public/photos/` (cropped from their Prepear recordings; mostly from recipe websites). Don't add more third-party photos without asking. Real photos will live in Netlify Blobs (Phase 1). A recipe without a photo shows plain soft grey with a muted chef hat (`.ck-photo-empty`), never a colored placeholder.

Before calling UI work done, scan the running app: `CHROME_PATH=/opt/pw-browsers/chromium-1243/chrome-linux64/chrome .claude/skills/impeccable/scripts/impeccable detect http://localhost:4173/` (after `npm run build && npx vite preview --port 4173`). Also run **`npm run check:ui`** (with the preview server running): it taps through interactive states (selected segments, swiped rows, open sheets and action sheets, the editor), runs axe contrast checks and flags overlapping buttons, and saves screenshots to `ui-states/`. **Look at those screenshots** before saying UI work is done. - Impeccable guidance never overrides the Framework7 rules above: no hand-built animations, gestures or z-index.

## Stack
Vite + TypeScript, TanStack Query, Zod, vite-plugin-pwa, `parse-ingredient`, Vitest.
Everything runs on **Netlify**: static hosting, Netlify Functions (API), Netlify Database (Postgres), Netlify Blobs (photos), Netlify Identity with Google sign-in (invite-only, the user's account only). Do NOT add Supabase or any second service; the user wants one.
Live site: https://cookbk.netlify.app

### Where things are (Phase 1)
- `src/lib/recipe.ts`: the recipe shape (Zod), shared by the app and the API. `src/lib/ingredients.ts`: parsing and scaling (tests beside it; run `npm test`).
- `src/data/`: `api.ts` (the API client, plus a **demo backend** used on `localhost` so the UI check runs without sign-in), `identity.ts` + `auth.tsx` (Netlify Identity with Google through **gotrue-js, the same way as the user's HPDE app**: the sign-in lives in localStorage only, never cookies, which iOS drops when it closes the home-screen app; every API call sends `Authorization: Bearer`; renewed when the app comes to the front; a renewal that fails offline doesn't sign out). **Only Identity refusing a renewal (or the API's 403, not an admin) signs out** (#114): a 401 from the API, or an Identity that can't answer (the API then says 503), is an error to try again. **Signing out only forgets this phone's copy, never gotrue-js's `logout()`**: Identity's logout ends every sign-in of the account at once, the home-screen app and every deploy preview included, which is what kept signing the user out (#114), `store.tsx` (TanStack Query, optimistic changes, IndexedDB cache; `useStore()` is what pages use).
- `netlify/functions/*.mts`: the API (v2 functions, `export default`), each checks `refuseUnlessAdmin(req)` first: it asks Netlify Identity (`/.netlify/identity/user`) whose Bearer token it is and requires the `admin` role (given in the Netlify UI; counts at once). `netlify/lib/`: shared server code, tested against a local Postgres (`@netlify/database-dev`).
- `netlify/database/migrations/`: SQL migrations applied by the deploy. **Never edit or delete one that has been deployed**; add a new one (`<timestamp>_<slug>.sql`). Never run DDL against the hosted database directly.
- Photos: picked and cropped on the phone, uploaded to Netlify Blobs (`photos` store) on save; the recipe stores their `/api/photos/<key>` addresses. Reading a photo needs no sign-in (`<img>` can't send the header; keys are random UUIDs); storing one needs the admin role. **Nothing deletes a photo when a recipe is saved or deleted**: a daily scheduled function (`netlify/functions/photo-cleanup.mts`, `netlify/lib/photo-cleanup.ts`, tests beside it) deletes a stored photo once no recipe has used it for 30 days (the list of unused photos and since when is kept in the `photo-cleanup` Blobs store; with no recipes at all it touches nothing). Deleting at once on save broke every copy still pointing at the old photo (deploy previews' copies of the database, screens holding the recipe from before the edit) once re-cropping became common (#51). Scheduled functions only run on the production deploy, whose database is the real one; previews share the photo store but must never decide what's unused.
- Prepear import (issue #14, `docs/PLAN.md` §6): `src/prepear/export.ts` is the export bookmarklet and `src/prepear/peek.ts` the peek (both self-contained: Settings → Import → From Prepear turns each function's own source into a bookmarklet). `npm run check:export` runs the export against a fake Prepear (add `BOOKMARKLET=<file>` to check the built one); `npm run check:peek` checks that the peek's file leaves out tokens, cookies and email addresses. `src/lib/prepear.ts` turns the export file into recipes (tests beside it); the import page copies photos through the server (`POST /api/photos` with `{ prepear }`, ImageKit only) and keeps the whole file in Blobs (`/api/imports/prepear`) for cookbooks (#25) and meal plans (#26). Imported recipes keep Prepear's ids in `prepearIds`, so importing again skips them. Never commit a real export or peek file; tests use made-up data (`scripts/fixtures/prepear-export-sample.json`). The peek file has real recipe data: it comes to Claude in chat, never into this public repo.
- New recipe from photos (issue #17): Recipes **+** is an action sheet (From photos or screenshots / Type it in). The editor (`RecipeEditPage`, prop `scanFiles`) shrinks the photos (`imageForReading`), sends them to `POST /api/read-recipe` (`netlify/functions/read-recipe.mts`), which keeps them in Blobs (store `reads`) and starts the **background function** `read-recipe-background.mts` (an ordinary function gets 30 seconds, too short for Claude); the phone asks `GET /api/read-recipe/:id` every 2s until it's done (`netlify/lib/read-recipe.ts`: `startJob`/`runJob`/`jobStatus`). Claude is reached through **Netlify's AI Gateway** (it gives functions `ANTHROPIC_API_KEY`/`ANTHROPIC_BASE_URL`; model `claude-opus-5-5` unless `READ_RECIPE_MODEL` is set; structured output in the shape `ReadRecipe`, `src/lib/read-recipe.ts`). The editor turns the reading into rows like the paste boxes (`withReading`: raw lines kept as written) and crops the dish photo out if Claude found one (`dishCrop`). The photos are deleted once read, the result once fetched. The demo backend answers with a made-up recipe; `?readfail` makes it fail (`check:ui` 12g0–12k).
- New recipe from a link (issue #15): Recipes **+** → From a link opens `FromLinkPopup` (a Framework7 popup with one Link field; opened without sliding and its field focused in the tap itself, since iOS only raises the keyboard then, and a field focused mid-slide made iOS shift the whole screen up). A web app can't read the clipboard by itself (iOS shows its Paste button every time), so the field is the only place to paste: the user rejected a separate Paste row and reading the clipboard from the action sheet. `linkIn()` finds the link in what's pasted; a link already imported, by `sameLink()` against `sourceUrl`, shows that recipe to open instead; Import opens the editor. The editor (`RecipeEditPage`, prop `scanUrl`) calls `POST /api/read-recipe` with `{ url }`. The server (`netlify/lib/web-recipe.ts`) fetches the page as iPhone Safari would, only public web addresses (`isPublicUrl`, redirects checked too). A page with a schema.org Recipe in its JSON-LD is read at once, without Claude (`recipeToReading`, the same `ReadRecipe` shape as photos) → 200 `{ status: 'done', url, recipe, photo }`. Any other page's text (`htmlToText`) is read by Claude as a job like the photos (`PAGE_SYSTEM`; `PageRequest`) → 202 `{ id }`. The page's photo comes back as a data URL for the phone to crop; the link becomes the recipe's `sourceUrl` (the full address, shown and editable in the editor as Source link; the recipe page shows only the site, linked), the site's name its source. Blocked sites and bot checks get a message pointing to From photos or screenshots. The demo backend answers any link with a made-up recipe and a sample photo; `?readfail` makes it fail (`check:ui` 12l–12p). The cloud sandbox can't reach recipe sites, so real pages can only be tried on a deploy preview.
- App updates: Settings → Version's refresh icon (`src/lib/appUpdate.ts`) lets the service worker look for a newer version, waits for one to take over, then **always reloads** the app (issue #91: the home-screen app has no pull-to-refresh, and the user taps it to get out of a bug). Every service-worker wait has a time limit (registration 3s, update 5s, take-over 10s), because on the iPhone one never answered and the icon spun forever; if the page is still there 4s after the reload, it opens the app afresh, and the icon stops after 30s at most (`check:ui` 13b4–13b5 make the service worker hang). A reload shows whatever the service worker has, including a version it took in the background. `/version.json` (written at build time by `vite.config.ts`, never kept offline) is no longer read; it stays for phones still on a build from before #91, which compare it to see they're behind. `npm run check:update` builds two versions and checks both cases (a version taken in the background, and nothing newer). Tapping the version itself copies it (issue #48). A reload the app does itself comes back to the tab it was on (`src/data/startTab.ts`, sessionStorage, read once by `App.tsx`); otherwise the app opens on Recipes.
- Cookbooks (issue #25): `src/lib/cookbook.ts` is the shape (recipe ids only; a recipe can be in several sections), `netlify/lib/cookbooks.ts` saves a whole cookbook in one transaction (three tables, migration `…_create_cookbooks.sql`; deleting a recipe takes it out of every cookbook), `/api/cookbooks`. Screens: `CookbooksPage`, `CookbookPage` (a cookbook and its sections), `RecipePickerPopup` (Add Recipes), `EditCoverPopup` (Edit Cover, issue #80: the plates, numbered 1 left, 2 middle, 3 right, from a grid of photos, and the card's colour), `OrganizePopup`, `AddToCookbookPopup`. `useCookbooks()` in `store.tsx`. A cookbook's card is a soft colour (`colorOf()`: the chosen `color`, else one picked from its id) with its cover recipes as plates, up to three `coverRecipeIds` in order (`coversOf()`; kept middle plate first, while Edit Cover numbers them left to right; `''` marks a plate filled in automatically with the cookbook's next photo: `spotsOf()`, `platesOf()`, `platePhotos()`, `coversFromSpots()`; the older single `coverRecipeId` is the middle plate's recipe); Uncategorized has a shelf and a page at `/cookbook/:id/section/uncategorized/`. Sort (issue #95): each cookbook's own, `manual` (its order, from Organize) unless one is picked, for its shelves, sections and search alike; kept in Settings as `cookbookSorts` (cookbook id → sort; manual has no entry), `sortRecipes()` in `src/lib/recipe.ts` (Recipes uses it too). A cookbook's page opens with a header in its colour, plates, name and counts, then its search bar, all page content that scrolls away (issue #90; see the approved exception above for the scroll listener that hands over to the bar's docked search bar). A section's page keeps the plain bar. Bar buttons over a recipe's photo are `--ck-overlay-button` circles with white icons; over a cookbook's pastel header, back and ⋯ are frosted white (`--ck-frosted-button`), turning into the usual bar buttons once the bar is solid. Prepear's cookbooks come in from the kept export (`src/lib/prepear-cookbooks.ts`, step 3 of Import from Prepear), skipping ones brought in before (`prepearId`).
- Planner (issues #62, #67, the Plan tab; not meal plans, #26): what's planned for real days. `src/lib/planner.ts` is the shape (`{ id, day: 'YYYY-MM-DD', recipeId | note, meal?, servings?, createdAt }`: a recipe or a note, in a meal slot or for the whole day, at the servings picked on the recipe page; a day being the phone's calendar day, no time zone) and the date helpers (weeks start on Monday); table `planned_recipes` (migrations `…_create_planned_recipes.sql`, `…_planner_meals_notes_servings.sql`; deleting a recipe takes it off every day), `netlify/lib/planner.ts`, `/api/planner`, `usePlanner()` in `store.tsx`. Screens: `PlanPage` (the week strip `WeekStrip`, a Swiper of weeks in the navbar's subnavbar, and the week's agenda), `NotePopup` (a note's own screen with a big field, #74; opened and focused in the tap by `openNote()`, like From a Link), `pickDay()` (Framework7's Calendar in a sheet: Move, Go to a day, the recipe page's Add to Planner). A planned recipe opens at its servings (`/recipe/:id/?servings=6`). Scrolling the agenda picks the day at the top. The picked day lives in `src/data/plannerNav.ts` (the page is made anew when its tab goes back to its first page; a recipe page's Planned chips open the Planner on a day through it).

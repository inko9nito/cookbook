# Cookbook — instructions for Claude

Personal recipe PWA for one user on an iPhone. Mobile-first, iOS-native feel. Full plan: `docs/PLAN.md`.

## Non-negotiable: never hand-roll iOS UI
- UI library is **Ionic React 9** (`@ionic/react`, `@ionic/react-router`), **iOS mode** (`setupIonicReact({ mode: 'ios' })` in `src/ionic/main.tsx`), React Router 6. The screens are in `src/ionic/`.
- Use Ionic's components for every page transition, swipe-back, modal, card, sheet, action sheet, alert, popover menu, toast, list, swipe row, reorder, segment, range, checkbox, radio, accordion, date picker, skeleton and tab. **The user chose a UI library so that motion isn't hand-written** (trial 1, `/next/`, plain pages with hand-made transitions, was rejected: "it feels like a website"). Don't hand-write a transition Ionic has.
- Do **not** write custom CSS or JS for animations, transforms, gestures or z-index, except the approved ones below. Custom styling is limited to colours, spacing, corners and typography, through Ionic's CSS variables and `::part()` where it has them.
- If Ionic lacks something, **stop and ask the user** before building a custom version.
- Check the Ionic 9 docs (and `node_modules/@ionic/core` for the iOS styles and animations) for a component's props and parts before using it. Don't guess.
- **No iOS 26 look**, the agreed design: flat docked tab bar, titles on the left, separate round bar buttons, no liquid glass, **no backdrop blur anywhere** (iPhone Safari left blurred layers blank in v1, #25).
- **A page must never change into "Not found" while it slides away** (#141's recording after Delete): `CookbookPage` and `RecipePage` keep showing what they're deleting (`leaving`) as they go. A page still loading after a reload shows its shape (skeletons), never "isn't here" or "0 recipes" (#35).
- Ionic gotchas found: its checkbox swallows taps on anything inside its label, so rows with buttons in them (cook mode) put the box in `slot="start"` and the text beside it ticks the row; Ionic rounds a toolbar button on `::part(native)`; fullscreen content pads its start under the header (`::part(scroll) { padding-top: 0 }` to put a photo under the bar); React sets Ionic's props as properties, so `[value=…]`/`[tab=…]` selectors don't match in tests.
- **The tab bar is drawn by each tab's first page** (`TabBar` in `ui.tsx`, an `IonFooter`), not over the tabs: each tab keeps its own stack in Ionic's tabs (`/recipes/recipe/:id`, `/cookbooks/:id`, `/cookbooks/recipe/:id`, `/plan/recipe/:id`, `/settings/appearance`…), so a pushed page slides in over the tab's first page, bar and all, and covers it, as iOS does (the user: a tab bar on a child page is a dealbreaker), and back reveals that page as it was. Ionic's own `IonTabBar` is kept, hidden, for its tab switching and stacks; the pages' bars press its buttons. Tried first: child pages in a root outlet above `IonTabs`. Ionic's router then hid and unmounted the tab's page while a child was on screen, so the page behind a back swipe was blank and came back without its scroll position.
- **Back swipe, one gesture only** (both at once slid two copies of the pages, the user's recording): **in the Home Screen app, Ionic's own** (`swipeBackEnabled`; the live page follows the finger with its shadow and parallax), with the pages' history kept inside the app (`IonReactMemoryRouter`), so iOS has no page of the site to go back to; **in a Safari tab, Safari's**, which can't be turned off there. The pages are browser history entries, and Ionic then shows the page at once (`history.ts`). `?standalone` makes a browser behave as the Home Screen app (checks). The card swipes down from its top bar only (the halves stop the touch), as in the app.
- Toasts look like the app's: a small dark pill as wide as its words with the Tomato check (Ionic's toast `icon`, a base64 SVG: Ionic's icon loader rejects a utf8 one), above the page's footer (the tab bar, Start cooking, cook mode's tabs; `positionAnchor`). Ionic pads a toast's words 15px all round, which can't be reached from outside, so it's 50px tall to the app's 44.
- Menus are the app's pull-downs (#39) for every + and choice (meal, store, sort); action sheets only for confirmations (Discard Changes, Sign Out). They grow out of the button tapped and shrink back into it through Ionic's animation API (`menuEnter`/`menuLeave` in `ui.tsx`, 260ms in with iOS's ease, 180ms out, none with Reduce Motion); Ionic starts a popover's inside at opacity 0, so the animation must bring it in.
- Search fields, chips, the view switch and the week strip sit in the header under the bar in a plain `.ck-ion-header-extra`, not in an `IonToolbar` (on the iPhone the toolbar sized itself short and cut the chips in half). One search look everywhere (soft grey pill, placeholder on the left). A cookbook's header is as the app's: plates centred, its name and count on the left. Its search docks into the bar once its pill reaches the bar (#90), and its name shows in the bar only once scrolled under it (otherwise Ionic's page transition showed it for a moment). Segments are styled as the app's (the picked side dark).
- **Two ways of scrolling, for the user to compare** (Settings → Scrolling, `src/ionic/scroll.tsx`, localStorage `ck-ion-scroll`; the user leans to the old app's but worries that custom work brought #141's vanishing titles). **Like the old app** (default): Ionic has no bar that hides on scroll, so it's built to **Framework7's own rules and timing** (read from `framework7/components/navbar`; the user compares it against the old app frame by frame): `barOnScroll()` hides the title row once past the bar's height scrolling down and shows it scrolling up, near the top or at the end; the slide (`translateY` by the bar's height) and the fade of its title and buttons are 400ms `ease` (`.ck-ion-slide-header`, `.ck-ion-bar-hidden`); search and chips stay at the top and the strip under the clock stays solid. A see-through bar fills in over its own height (`--ck-fill`, held while hidden, as Framework7's transparent navbar), so over a recipe's photo it's clear at the top, then hides, then comes back solid. A cookbook (#90): plates and colour fade as they go under the bar (`--ck-hero-p`), the bar fills once they've gone, the name moves into the bar once all the way under it, the search hands over to the docked one when it reaches the bar (both always there, only one visible), and once docked the title row hides and shows the same way. **Everything is set straight on the elements as the page scrolls, never through React state**: a render per scroll frame made the cookbook's bar jitter. The toolbar's background is drawn at `::part(background)` with `!important` opacity, and a cookbook's bar title too, so Ionic's page slide can't animate them (it drew a recipe's bar solid while it slid in, then dropped it). A recipe or cookbook still loading after a reload shows its shape, never "isn't here" or "0 recipes". **iOS large titles**: Ionic's own `collapse="condense"` on the tabs, `collapse="fade"` on a recipe and a cookbook, no custom code. Both put the content under the bar (`fullscreen`), the arrangement #141 broke in Framework7. The five tabs share `TabPage`, which builds either.

## Seeing an issue's screenshots and videos (never say they're blocked)
The user attaches screenshots and screen recordings to issues and expects them looked at. `github.com/user-attachments/...` links can't be fetched from a cloud session (the GitHub proxy refuses non-repo paths, and `/markdown` too), but the issue's **rendered HTML** from the repo API carries signed `private-user-images.githubusercontent.com` addresses (valid 5 minutes), which download fine:
1. `curl -sS -H "Accept: application/vnd.github.full+json" https://api.github.com/repos/inko9nito/cookbook/issues/<n> -o issue.json` (comments: `.../issues/<n>/comments` with the same header; each has `body_html`). Save to the scratchpad.
2. Pull the `<img src="…">` / `<video src="…">` addresses out of `body_html` (unescape `&amp;`), write each to a file, then `curl -sS -o shot.png "$(cat url.txt)"` and look at it with Read.
3. A video only becomes a `<video>` (with a signed address) when its link is **on a line of its own**; inline in a sentence it stays a plain `github.com/user-attachments` link. Then edit the issue description (the plan lives there anyway) to put the link on its own line, and fetch again.
4. Videos: `ffmpeg -i vid.mov -vf "fps=3,scale=300:-1" frames/f%02d.png`, then `ffmpeg -i "frames/f%02d.png" -vf "tile=6x3" -frames:v 1 sheet.png`, and Read the contact sheet.

## Workflow: preview before merging
- Every change goes to the user as a **pull request with a Netlify deploy preview**: push to the working branch, open a PR into `main` if none is open (or keep updating the open one), and give the user the preview link `https://deploy-preview-<PR number>--cookbk.netlify.app` each time it updates.
- **Merge only when the user asks.** They look at the preview on the phone first.
- **Never watch (subscribe to) PRs in this repo**, and don't ask whether to. The user says when to merge.
- **Plans live in their GitHub issue.** For an issue worked through in steps (e.g. #14, the Prepear import), keep the plan in the issue's description: tick steps as they land, note decisions and open questions, and add a dated line under Status at each milestone (PR opened, waiting on the user, merged). ## Design: the Cookbook design system
- Spec: `DESIGN.md`. Tokens: `src/theme/cookbook.css` (it still holds v1's Framework7 rules too, inert in v2: prune them as screens are matched); v2's styles: `src/ionic/ionic.css`. Visual check: in-app Settings → Appearance (the Style Guide).
- The user picked each component's shape from a different design system (RED, Starbucks, Headspace, Pinterest, Instacart, DoorDash; recipe cards from Prepear itself) and unified all colors: Cool grey neutrals, **Tomato `#e4572e`** accent, **Parkinsans** at 90% for all text (issue #135; Fredoka + Nunito before). Light mode only for now.
- Never hard-code colors in components. Use `var(--ck-*)` tokens or Ionic's variables. Add new tokens to `cookbook.css` and `DESIGN.md` (both the YAML front matter and the prose) together.
- **Edges (#55):** a shaped button at a popup's edge is as far from the top as from the sides, 16px (`--ck-edge-inset`; popup headers are 72px: 16 + 40px buttons + 16). A sheet keeps 24px from every edge (`--ck-sheet-inset`, mapped onto Framework7's block, list, toolbar and calendar variables in `.sheet-modal`): its header text 24px from the top and sides, its content lined up with it. `check:ui` flags any open popup or sheet that breaks either.
- **Empty states (#118):** a screen with nothing on it uses `EmptyState` (`src/components/ui/EmptyState.tsx`) and the rules in `DESIGN.md` → Empty states: hide what works on things that aren't there (search, view switches, sort, counts), a few words, one button that opens the same choices as the screen's +, no instructions. An empty *part* of a screen keeps the small inline look (#82). One icon on a white circle (the user rejected plates there: they mean cookbooks); Style Guide → Empty state shows it.
- Tomato for **text** is `--ck-accent-ink` `#c4421c` (also Ionic's primary); bright Tomato `--ck-accent` is for fills only. Muted text is `#6e6e73`. These were chosen to pass WCAG AA contrast.
- **Icons: Lucide only** (`lucide-react`, the same library as the user's other apps). Don't add another icon set. Ionic's built-in glyphs (back chevron, list chevrons, checkmarks, search magnifier) stay as they are.
- The repo is public. The user explicitly approved committing the sample photos in `public/photos/` (cropped from their Prepear recordings; mostly from recipe websites). Don't add more third-party photos without asking. Real photos will live in Netlify Blobs (Phase 1). A recipe without a photo shows plain soft grey with a muted chef hat (`.ck-photo-empty`), never a colored placeholder.

### Where things are (Phase 1)
Screen and popup names below (`…Page`, `…Popup`, `src/components/`, `src/pages/`) and `check:ui` step numbers are v1's, on `v1-framework7`; v2's screens are in `src/ionic/` (one file per screen or group: `RecipesPage`, `RecipePage`, `EditPage`, `CookbooksPages`, `PlanPage`, `GroceriesPage`, `SettingsPages`, `CookMode`, `modals`, `sheets`, `ui`, `scroll`, `history`). The data layer (`src/data`, `src/lib`) and the server are the same for both.
- `src/lib/recipe.ts`: the recipe shape (Zod), shared by the app and the API. `src/lib/ingredients.ts`: parsing and scaling (tests beside it; run `npm test`).
- `src/data/`: `api.ts` (the API client, plus a **demo backend** used on `localhost` so the UI check runs without sign-in), `identity.ts` + `auth.tsx` (Netlify Identity with Google through **gotrue-js, the same way as the user's HPDE app**: the sign-in lives in localStorage only, never cookies, which iOS drops when it closes the home-screen app; every API call sends `Authorization: Bearer`; renewed when the app comes to the front; a renewal that fails offline doesn't sign out). **Only Identity refusing a renewal (or the API's 403, not an admin) signs out** (#114): a 401 from the API, or an Identity that can't answer (the API then says 503), is an error to try again. **Signing out only forgets this phone's copy, never gotrue-js's `logout()`**: Identity's logout ends every sign-in of the account at once, the home-screen app and every deploy preview included, which is what kept signing the user out (#114), `store.tsx` (TanStack Query, optimistic changes, IndexedDB cache; `useStore()` is what pages use).
- `netlify/functions/*.mts`: the API (v2 functions, `export default`), each checks `accountFrom(req)` (`netlify/lib/http.ts`) first: it asks Netlify Identity (`/.netlify/identity/user`) whose Bearer token it is and requires a role (given in the Netlify UI; counts at once). Things that use Claude (reading recipes, naming groceries) or Prepear's import check `refuseUnlessAdmin(req)`.
- **Accounts (issue #146):** `admin` opens the original cookbook (owner `''`) with everything. `user` opens **a cookbook of its own**, kept under its Identity id, without Claude or Prepear (the user's choice): Recipes + goes straight to Type it in, Settings has no Import, grocery names come only from its own corrections and the rules (never Claude, never the admin's). Every table has `owner_id` (migration `…_owners.sql`; settings and grocery names are keyed per owner); every query in `netlify/lib/` takes the owner and filters by it, and every save leaves another owner's row alone (ids come from the phone: `ON CONFLICT … WHERE owner_id = EXCLUDED.owner_id`, else `NotYours` → 409), and only the owner's recipes can go in a cookbook, the Planner or the list. Only the photo clean-up reads everyone's recipes (`listAllRecipes`): the photo store is shared. On the phone `useAccount()` (`/api/account`) says `{ admin }`; hidden until known. Locally `?user` makes the demo a user (`check:ui` 40y–y2). `owners.test.ts` checks the two stay apart. `netlify/lib/`: shared server code, tested against a local Postgres (`@netlify/database-dev`).
- `netlify/database/migrations/`: SQL migrations applied by the deploy. **Never edit or delete one that has been deployed**; add a new one (`<timestamp>_<slug>.sql`). Never run DDL against the hosted database directly.
- Photos: picked and cropped on the phone, uploaded to Netlify Blobs (`photos` store) on save; the recipe stores their `/api/photos/<key>` addresses. Reading a photo needs no sign-in (`<img>` can't send the header; keys are random UUIDs); storing one needs the admin role. **Nothing deletes a photo when a recipe is saved or deleted**: a daily scheduled function (`netlify/functions/photo-cleanup.mts`, `netlify/lib/photo-cleanup.ts`, tests beside it) deletes a stored photo once no recipe has used it for 30 days (the list of unused photos and since when is kept in the `photo-cleanup` Blobs store; with no recipes at all it touches nothing). Deleting at once on save broke every copy still pointing at the old photo (deploy previews' copies of the database, screens holding the recipe from before the edit) once re-cropping became common (#51). Scheduled functions only run on the production deploy, whose database is the real one; previews share the photo store but must never decide what's unused.
- Prepear import (issue #14, `docs/PLAN.md` §6): `src/prepear/export.ts` is the export bookmarklet and `src/prepear/peek.ts` the peek (both self-contained: Settings → Import → From Prepear turns each function's own source into a bookmarklet). `npm run check:export` runs the export against a fake Prepear (add `BOOKMARKLET=<file>` to check the built one); `npm run check:peek` checks that the peek's file leaves out tokens, cookies and email addresses. `src/lib/prepear.ts` turns the export file into recipes (tests beside it); the import page copies photos through the server (`POST /api/photos` with `{ prepear }`, ImageKit only) and keeps the whole file in Blobs (`/api/imports/prepear`) for cookbooks (#25) and meal plans (#26). Imported recipes keep Prepear's ids in `prepearIds`, so importing again skips them. Never commit a real export or peek file; tests use made-up data (`scripts/fixtures/prepear-export-sample.json`). The peek file has real recipe data: it comes to Claude in chat, never into this public repo.
- New recipe from photos (issue #17): Recipes **+** is an action sheet (From photos or screenshots / Type it in). The editor (`RecipeEditPage`, prop `scanFiles`) shrinks the photos (`imageForReading`), sends them to `POST /api/read-recipe` (`netlify/functions/read-recipe.mts`), which keeps them in Blobs (store `reads`) and starts the **background function** `read-recipe-background.mts` (an ordinary function gets 30 seconds, too short for Claude); the phone asks `GET /api/read-recipe/:id` every 2s until it's done (`netlify/lib/read-recipe.ts`: `startJob`/`runJob`/`jobStatus`). Claude is reached through **Netlify's AI Gateway** (it gives functions `ANTHROPIC_API_KEY`/`ANTHROPIC_BASE_URL`; model `claude-opus-5-5` unless `READ_RECIPE_MODEL` is set; structured output in the shape `ReadRecipe`, `src/lib/read-recipe.ts`). The editor turns the reading into rows like the paste boxes (`withReading`: raw lines kept as written) and crops the dish photo out if Claude found one (`dishCrop`). ## Data rules
- Always keep the raw ingredient line exactly as typed, alongside the parsed fields.
- Cookbooks, meal plans and ingredients made from another recipe (`recipeId`, issue #11) reference recipes by id. Never copy recipe data into them.
